## 1. CONVENTIONS.md

### What holds

- `// SPDX-License-Identifier: MIT OR Apache-2.0` is the first line of every `.rs` and `.cu` file.
- `Cargo.toml`'s `[lints]` matches the lint-floor table entry for entry; `#![deny(warnings)]`, the MSRV
  lint guard, and the one crate-root policy (`many_single_char_names`) with its reason.
- No direct indexing in `src/`; every `as` carries `// CAST:` and its `#[allow]`
  (`src/cuda.rs:34–58`); kernel arguments go through `i32_of` / `u32_of` / `i64_of`.
- `unsafe` only in `src/cuda.rs` (allocations, launches) and `examples/compare.rs` (profiler calls),
  all behind `cuda`; the CPU twin is what the CUDA path is tested against.
- Launch arguments in signature order and type, for all three kernels (checked one by one against the
  `extern "C"` lists); everything on candle's stream; `alloc` only for buffers the kernels write
  entirely, each `SAFETY` naming the writer.
- Kernels: `__launch_bounds__(NT)` on all three; `ORDER` at both ends of the handshake; `DETERMINISM`
  on every cross-thread or cross-block reduction; no floating-point atomics; the float4 precondition
  stated in the kernel and checked in Rust.
- The saved-state pattern: `Mutex<Option<Tensor>>`, cloned not taken, a poisoned lock and a backward
  before the forward are errors (its documentation: A1).
- The determinism test compares `to_bits()`, 8 reruns, causal and not, both entry points.
- Python: 2 spaces, ≤ 100 columns, double quotes, module docstrings, doctests passing.

## 2. Correctness and robustness

### B1 — High — compute capability 7.5 (Turing) cannot run the kernels; every document says 7.0+

**Stated:** README badge (`README.md:9`, "sm_70+") and Limits (`:116–118`), crate docs
(`src/lib.rs:62–66`), tutorial (`docs/tutorial.md:22–23`, `:202`). The devlog adds (FA7) "with CUDA 13
the buildable floor is 7.5 (Turing)".

**Fact:** the opt-in shared memory per block is 96 KB on 7.0 but **64 KB (65,536 B) on 7.5**, below the
forward's 69,632 B and the backward's 87,552 B. `function()` raises `MAX_DYNAMIC_SHARED_SIZE_BYTES`, and
on a T4 or an RTX 20xx that call fails: the first call returns `DriverError(CUDA_ERROR_INVALID_VALUE)`.
With CUDA 13 (no sm_70 / sm_72 target), the effective floor is therefore **8.0**; with CUDA 12, Volta
(7.0) fits. And no card below 8.0 has ever run the kernels: the < 8.0 load path is tested only by forcing
it on sm_120 (`CANDLE_FUSED_ATTN_SYNC_LOADS`).

**Evidence:** arithmetic against the CUDA programming guide's per-capability limits; not run on Turing
hardware.

**Fix:** "8.0 or newer; 7.0 (Volta) with a CUDA 12 toolkit; not 7.5 (Turing: 64 KB of shared memory per
block)" wherever the floor is stated. Before `set_attribute`, read
`CU_DEVICE_ATTRIBUTE_MAX_SHARED_MEMORY_PER_BLOCK_OPTIN` and fail with "fused_attention: the backward needs
87,552 B of shared memory per block, this GPU allows N".

### B2 — Medium — empty inputs panic on CUDA

`fused_attention_qkv` with batch 0 or seq 0 on CUDA **panics**: `cuda::view` (`src/cuda.rs:282–284`)
calls cudarc's `CudaView::slice`, which is `try_slice(..).unwrap()` (cudarc 0.19.10,
`src/driver/safe/core.rs:2009`), with an offset (`hd`, `2·hd`) past an empty storage. Verified:
`called Option::unwrap() on a None value`. The same call on the CPU returns an error (candle's `empty
tensor for reduce`); `fused_attention` with batch 0 on CUDA returns `DriverError(CUDA_ERROR_INVALID_VALUE)`
(a zero grid). `src/lib.rs:359` and `:361` use the same panicking `slice`.

Grit denies `unwrap` and `panic` so that the library never panics; a callee's `unwrap` defeats it. Use
`try_slice` with `ok_or_else`, and choose one behaviour for empty inputs on both devices: an empty output
(as candle's own ops do) or a prefixed error.

### B3 — Low — an odd `head_dim` gets an alignment error

On CUDA, `fused_attention_qkv` with `head_dim` 6 returns `fused_attention_qkv: rows must be 16-byte
aligned` (verified): the stride check (`src/lib.rs:533`) runs before the head-dim gate
(`src/cuda.rs:150`), and the head stride is `d`. Check the head dimension first.

### B4 — Low — grid limits surface as a raw driver error

Batch and heads become `gridDim.z` and `gridDim.y`, limited to 65,535; `u32_of` only checks u32
(`src/cuda.rs:97–103`). Batch 65,536 → `DriverError(CUDA_ERROR_INVALID_VALUE)`; 65,535 → ok (verified).
Check and say so, or fold `b·h` into `gridDim.x` (2³¹ − 1).

### B5 — Low — deadlock freedom rests on dispatch order

Documented at `fused_attn.cu:199–200`: a block waits only on lower key blocks, assumed dispatched first.
That is CUTLASS's serial split-K assumption, not a CUDA guarantee. A ticket (`atomicAdd` on a per-(b, h)
counter, handing out key-block indices in arrival order) removes it for one atomic per block, without
changing any arithmetic (bitwise neutral). Optional.

### B6 — Info — the kernels' logic: reviewed, no defect found

Traced by reading: launch arguments against each `extern "C"` signature; every element of the five
uninitialised allocations written before it is read (`o`, `lse` by the forward; `dsum`, `turn` by the D
kernel; `dqkv` by the owning key blocks and, for dQ, key block 0 first). Causal included: key block 0
visits every query tile, and tile *t* is visited by exactly the blocks *kb* ≤ ⌊*t*/2⌋ that the `last`
formula expects. Also traced: the turn handshake (release after every thread's fence and a barrier;
acquire, fence, barrier, then L2-only loads), the cp.async double-buffer hazards (each buffer refilled
only after the barrier ending its last read), 16-byte alignment of every float4 and cp.async address
given the Rust checks, and 64-bit offset arithmetic.

Run on the GPU, the copy fallbacks agree with the CPU: qkv at offset 1, out 4.8e-7 / grad 5.4e-7; a
transposed gradient, grad 8.3e-7; aligned, 4.8e-7 / 6.0e-7.

## 3. The speed lead: how fragile, and what guards it

The margins, from the five 0.4.0 reports (b 64 · h 6 · s 240 · d 64, non-causal, same session per card):

| card | kernel, fwd: ours / SDPA | kernel, fwd + bwd net | wall, fwd | wall, net of head | wall, training call |
|---|--:|--:|---|---|---|
| RTX 5060 Ti | 0.781 / 0.903 (−14 %) | 3.733 / 4.621 (−19 %) | ours ×1.19 | ours ×1.14 | SDPA ×1.19 |
| RTX 5090 | 0.178 / 0.206 (−14 %) | 0.813 / 1.022 (−20 %) | ours ×1.22 | **ours ×1.07** | SDPA ×1.17 |
| RTX 4090 (350 W cap) | 0.255 / 0.333 (−23 %) | 1.183 / 1.555 (−24 %) | ours ×1.34 | **SDPA ×1.11** | SDPA ×1.56 |
| RTX 3090 | 0.580 / 0.832 (−30 %) | 2.337 / 3.522 (−34 %) | ours ×1.41 | ours ×1.21 | SDPA ×1.13 |
| A100 | 0.625 / 0.438 (+43 %) | 2.856 / 1.650 (+73 %) | SDPA ×1.32 | SDPA ×2.09 | SDPA ×2.53 |

The kernel lead on GeForce cards is 14–34 %. The lead a training loop feels is thinner: ×1.07 net on
the 5090, reversed on the 4090. Every gross training call is SDPA-faster, because candle's own loss head
and autograd cost 0.32–1.85 ms where `PyTorch`'s cost 0.07–0.29 ms. The fragility therefore has three
sources:

- kernel codegen (P1–P4);
- the wrapper's silent copies (P5);
- what surrounds the kernels: candle's gradient accumulation (P6) and host time (P7).

### P1 — High — the backward's bits depend on the driver's JIT

**Mechanism.** The crate ships PTX, and the driver compiles it at load. A PTX `mul.f32` / `add.f32` /
`sub.f32` without a rounding modifier may be fused into an FMA by that compiler (PTX ISA: "mul/add
sequences with no rounding modifiers may be optimized to use fused-multiply-add instructions"). The
current PTX has 306 such instructions.

**Measured.** Compiled by the toolkit's ptxas (13.1, sm_120a) with `--fmad=true` and `--fmad=false`, the
forward and D kernels are identical. The backward differs by exactly 16 FFMA: 528 against 512 (FMUL 72
against 88, FADD 40 against 56). All 16 come from `fused_attn.cu:309`, `expf(s[r][jj] * scale - li)`: 16
per thread per tile, mapped through `-lineinfo`. P feeds dV, and through dS, dK and dQ. Whether those 16
operations round once or twice therefore decides every gradient bit, and that decision belongs to the
JIT of whichever driver is installed.

**Consequence.** "Reruns are bit-identical" holds per (build, driver, card); the tests and the bitwise
gates all ran under one driver at a time. **A driver update can change every gradient bit of an
unchanged build**: exactly the "reproducible across days" the ROADMAP's users need.

The forward is safe today, but `:538` + `:548` (`s * scale`, then `s − m_new`) is the same pattern, legal
for a future JIT to fuse. Independently, `expf` lowers to `ex2.approx` (36 sites), whose results are
implementation-defined per architecture. Bit identity across architectures is therefore not available
even after pinning, and no document should imply it.

**Fix.** Bit- and speed-neutral on today's toolchain; confirm with `bench/bitwise.py` against v0.4.0 and
an A/B.

- `:309`: `fmaf(s[r][jj], scale, -li)` (what ptxas does today).
- `:538`: `__fmul_rn(s[r][jj], scale)` (what it does today).
- `:55`: the D kernel's two products as an explicit `fmaf`, in today's order.
- Then a tripwire: the SASS of `ptxas --fmad=true` and `--fmad=false` must be identical for all three
  kernels, so nothing is left to the JIT.
- State the scope in the README and the tutorial: bit-identical reruns on one machine (build, driver,
  card).

### P2 — Medium — on sm_80, ptxas gives the forward 80 registers

ptxas cannot see dynamic shared memory. Without a minimum-blocks hint it sizes registers for an occupancy
the 68 KB block cannot reach. Measured with `ptxas -v` (toolkit 13.1):

| kernel | sm_120a | sm_89 | sm_86 | sm_80 | sm_80 with `__launch_bounds__(NT, 2)` or `(NT, 1)` |
|---|--:|--:|--:|--:|--:|
| forward | 114 | 122 | 122 | **80** | 128 |
| backward | 128 | 128 | 128 | 128 | — |
| D | 24 | 20 | 20 | 20 | — |

There are no spills anywhere. On the A100 the forward runs two blocks per SM (2 × 69,632 B ≤ 164 KB), and
two blocks at 128 registers still fit (2 × 256 × 128 = the 65,536-register file). So
`__launch_bounds__(NT, 2)` states the true occupancy and frees 48 registers per thread: the resource
FA7's pipeline used on the 5060 Ti (80 → 114). This is an unmeasured candidate for the ROADMAP's A100
item, where SDPA's forward is 1.43× faster. It changes no arithmetic, but gate it anyway.

Related: the shared-memory carveout is left to the driver. `CU_FUNC_ATTRIBUTE_PREFERRED_SHARED_MEMORY_CARVEOUT`
would guarantee the two-block split (not checked whether the default already gives it).

### P3 — Medium — nothing watches the codegen

The devlog shows how sensitive the kernels are to what the source does not show:

- runtime loop bounds, +14.2 % (FA15: fixed-trip unrolling lost);
- half the threads, +15.5 % (FA11);
- register allocation (P2);
- contraction (P1).

Today a change's codegen effect is learnt only from a GPU A/B. Proposal: a committed `bench/codegen.txt`,
generated by a CPU-only script (nvcc + ptxas + cuobjdump; everything in P1–P2 took seconds). For each
kernel × {sm_80, sm_86, sm_89, sm_120a}, it lists:

- registers, spills and barriers;
- SASS counts of FFMA, FMUL, FADD, LDS, LDGSTS, BAR and BRA;
- P1's fmad equality.

`ci-local.sh` regenerates and diffs it. A comment-only edit must leave it unchanged; an intended change
shows its delta before any GPU time is spent, and the A/B and its report then explain the delta.

### P4 — Medium — the twinned constants look tunable and are not

The thread mappings hard-code NT 256, HD 64, FW_QRYS 64, KB_QRYS 32 and KB_KEYS 64:

- `ty = tid / 16` with `r0 = 4·ty` (64 rows), and `d0 = 4·tx` (64 dims);
- `half = tid / 128`, `j0 = 4·(u / 8)`, `i0 = 2·(tid / 16)`;
- the D kernel's `lane` / `lane + 32`;
- `q_begin` and `last`, which need KB_KEYS to be a multiple of KB_QRYS;
- LD ≡ 4 (mod 32), for conflict-free float4 phases.

Changing one constant on both sides, as the TWIN rule invites, compiles and computes wrong results. Add a
`static_assert` in the `.cu` for each assumption.

The same holds for shared memory: the carve-up (`fused_attn.cu:222–229`, `:476–480`) and the Rust sizes
(`src/cuda.rs:51`, `:57`) are twins nothing checks. A buffer added on the kernel side overruns shared
memory silently. The cheapest robust check: a tiny `fattn_constants` kernel that writes the `.cu`'s
constants and carve-up byte counts to a buffer, compared with the Rust constants in a CUDA test.

### P5 — Medium — silent copy cliffs in the wrapper

These layouts are copied without any signal (`src/lib.rs:112–118`, `:172–178`, `:370–380`):

- a qkv whose offset or batch / seq stride is not a multiple of 4 floats;
- q / k / v failing `float4_aligned`;
- an unaligned gradient.

The copies are correct (B6). But at the canvas shape a qkv copy moves 70.8 MB in and out per forward,
plus the copy's backward. An upstream layout change (an extra column, a slice of a larger projection)
would invisibly cost more than FA14 saved. Expose a predicate, e.g. `reads_in_place(qkv: &Tensor) ->
bool` (and one for q / k / v), so that callers such as candle-mi can assert the fast path in their
tests. State the cost in `# Shapes` (A12).

### P6 — Medium — a tenth to a sixth of "forward + backward" is candle's gradient accumulation

Stock candle 0.11 accumulates every custom-op gradient as `zeros_like(arg)` plus an `add`
(`candle-core-0.11.0/src/backprop.rs:662–666`, `:768–777`). A qkv training call therefore carries a
qkv-sized `badd` that the loss-head phase does not. From each 0.4.0 report's per-kernel line (the
published net, against the three `fattn_*` kernels alone):

| card | net (ms) | attention kernels | glue in net | kernels-only ratio to SDPA's `fmha` | net ratio |
|---|--:|--:|--:|--:|--:|
| RTX 5060 Ti | 3.733 | 3.151 | 0.582 (15.6 %) | 1.29× | 1.24× |
| RTX 4090 | 1.183 | 0.986 | 0.197 (16.7 %) | 1.34× | 1.31× |
| RTX 5090 | 0.813 | 0.698 | 0.115 (14.1 %) | 1.30× | 1.26× |
| RTX 3090 | 2.337 | 2.083 | 0.254 (10.9 %) | 1.53× | 1.51× |
| A100 | 2.856 | 2.599 | 0.257 (9.0 %) | 0.55× | 0.58× |

This is fair as "what the trainer pays", and SDPA's net carries `PyTorch` glue too (a 353 µs
`CatArrayBatchedCopy` on the 5060 Ti). But it ties the headline to candle's version. A candle that stores
the first gradient instead of adding it to zeros would move every net number with no change here; the
`gradstore-accumulate-0.11` fork branch of devlog FA2 suggests one exists.

Print the attention-kernel time beside the net in `compare.py`'s report (the per-kernel data is already
there), and keep "stock candle 0.11" next to the README's table.

### P7 — Medium — in wall time the lead is thin or reversed

See the table at the top of § 3. The README's Measured section says "kernel time", correctly. But the
A100 "1.7×" (`src/lib.rs:71`, `CHANGELOG.md:15`, `docs/tutorial.md:204`) names no instrument, and in wall
time net of the head SDPA leads by 2.09×.

The thinnest consumer-card margin is the 5090's wall-time net, ×1.07. There, host-side changes (candle,
the wrapper) weigh as much as kernels. Add one wall-time line per card to the README, and the instrument
wherever "1.7×" appears.

### P8 — Medium — `box.sh` still measures against 0.3.0

`bench/box.sh:18` and `bench/remote_box.sh:42` default to `BASE=v0.3.0`, and README `:127` and tutorial
`:190–191` say so. After 0.4.0, the next lever measured with the defaults includes FA14's backward gain
(−5.6 to −6.9 %): a change 3 % slower than 0.4.0 would still read about −3 %. Default to the latest
release tag (or `git describe --tags --abbrev=0 --exclude '*-*'`).

### P9 — Low — speed measured at one shape

Every comparison is at b 64 · h 6 · s 240 · d 64, non-causal. The devlog shows the result moves with
batch against L2 (FA13) and with S mod 64 (FA15: 12.1 % dead work at S = 240). The README names its
shape, but the Limits and the tutorial do not say the lead is unmeasured elsewhere, and no causal
comparison is committed. A small sweep on the 5060 Ti (s 128–1024, causal on and off) would bound the
claim.

### P10 — Low — the build follows the toolkit, the run follows the driver

The PTX comes from whichever `nvcc` is on PATH. cudaforge reruns on `CUDA_COMPUTE_CAP` and `NVCC_CCBIN`,
not on a toolkit switch (`CUDA_PATH`), and its OUT_DIR cache keys on arch and arguments, not on the nvcc
version: a switched toolkit can keep a stale PTX. A build with `CUDA_COMPUTE_CAP` below 80 (say, a fleet
that includes a V100) silently drops both cp.async paths on every card (−40 % forward, −14 % backward by
FA7 / FA9), with no sign at runtime.

Emit `cargo::rerun-if-env-changed=CUDA_PATH`, and a `cargo::warning` naming the target and whether
cp.async is compiled in. Longer term, embed SASS for the build's architecture with the PTX as fallback (a
fatbin): the code that runs is then the code that was measured, which also settles P1 for that
architecture. (`-O3` in `build.rs` is a host-code flag for `nvcc`; device code is optimised by default.
Harmless.)

### P11 — Info — the crate's own host cost is small

Forward wall time 0.798 ms against 0.781 ms of kernel (5060 Ti). Per launch: one global mutex and a hash
lookup (`src/cuda.rs:113–120`), stream-ordered allocations, no synchronisation.
